## Rules that apply throughout

- Pages and APIs derive the signed-in account from the session; every protected API handler must perform its own sign-in check, and user data queries must be scoped by `user_id`. Worker-token routes use their own token check.
- Production builds of the hosted app allow session, Claude-token, and picture-worker access only for members of the one circle in `DS_FAMILY_CIRCLE_ID`; missing or invalid configuration denies access. Local PGlite copies do not use the hosted circle gate.
- Development uses a separate dev database (`DATABASE_URL` in `.env.development.local`, for example a Neon branch such as `ep-your-dev-branch-123456`); builds and scripts may use the live one (`.env.local`). Read `before-you-code` and `add-migration`; inspect the target before any migration or seed. The owner runs live migrations/seeds.
- Migrations are additive and idempotent; code must handle documented missing-table/column cases while a change is not yet on live.
- UI uses the shared components and tokens in `components/ui/` and `app/globals.css`, not hard-coded colors or inline style attributes.
- The person is the author of their meanings. Traditional claims need sources; the AI companion receives only the person's own words and nothing is sent until the person sees the “Show what would be sent” screen.
- Never push to a remote unless the owner explicitly asks; the repository hook asks the user before any push (changed from a hard block on 2026-10-22).
